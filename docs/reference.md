# Agent Orchestrator reference

## Introduction

Agent Orchestrator lets a set of small local language models build software together, one verified step at a time. Instead of asking one large model to write a whole project, it splits the work across three specialised roles served by llama.cpp on your own machine, and it refuses to move forward until an independent reviewer approves each step.

## Description

You describe the goal, constraints, and completion criteria in a `PROJECT.md`. **Start project** (`python orchestrator.py --project <folder> [--once]`) then runs the **lead project run**: the lead agent (the Planner role, `prompts/lead_project.txt`) works through `PROJECT.md` on its own with a Code turn's tools (list/read/search/write/replace files, `todo`, the sandboxed `run_command`, `run_checks`, `delegate` to fresh Implementer/Reviewer sub-agents, and the conversation's web search, utilities and skills when they are switched on; the launcher passes them as a Code request with `--request <request.json>`, and the project stays the first folder), verifies with `run_checks` (which returns the error details: file, line, message, command output, clipped to about 3,000 characters) and by reading files, and records each finished item with `record_progress(item, outcome)`, which appends `## Done: <item>` (time, outcome) to `STATE.md` and sets `Last done` in `HANDOFF.md`. `finish(summary)` ends the run with exit code 0 and the `## Project complete` section in `STATE.md`. The lead's input is `PROJECT.md`, `STATE.md` and a file inventory, so a new run resumes after the recorded items. `--once` stops after the first recorded item. `max_lead_steps` (default 200) caps the lead's model calls per run (each delegation keeps its own `max_tool_steps`); hitting it, or a fatal model error, prints an `ERROR:` line and exits 1. Long runs are kept workable by the in-request context compaction. The project folder may not overlap this folder. Its file tools reach the whole project root except `api_key.txt` and `.git`. The run's output streams into the Code conversation and shows the lead and its workers on their cards (the usual `loading`, `model`, `delta`, `usage`, `tool` events); each recorded item is a `task {id: item, outcome}` event followed by `task_end` and `task_start`, and `finish` emits `complete {summary}`.

`--pipeline` runs the legacy bounded loop instead:

`planner -> implementer tools -> reviewer -> fix/review -> verified state -> planner`

- **Planner** reads the project and the verified state, then picks one feature-sized task: one user-visible feature or behaviour across the files it needs, up to 5 files and 10 required-work items by default.
- **Implementer** writes code with file tools limited to those files, and can run only the validation commands you have approved.
- **Reviewer** is read-only. It judges the diff and validation evidence and returns `PASS` or `FAIL`.
- **Verified state** (`STATE.md`) advances only after a `PASS`, so the next task always builds on reviewed work.

The sections below on task limits, the configurator, the contract, the behaviour and code checks as gates, checkpoints and review rounds describe this legacy pipeline.

Models are loaded one at a time on a local llama-server, so the three roles can share a single GPU, and the server is stopped again when a run ends. A Windows launcher (`dist\Agent Orchestrator.exe`) wraps the Python engine with project setup, live model output in the conversation, per-model token statistics, and a saved execution log.

The engine uses only Python's standard library and llama-server's OpenAI-compatible API. The implementer can only touch the files named by the planner; the per-task limits are `"task_limits": {"max_allowed_files": N, "max_required_work": M}` in the project's `config.json` (defaults 5 and 10; set them in the launcher under Project > Task limits). The reviewer is read-only. Shell access is not general-purpose: models can only run commands you explicitly name in `validation_commands`.

**Requirements:** Windows, Python 3.11+ on `PATH`, `llama-server.exe` (the launcher downloads it), and the three models as GGUF files in the Hugging Face cache or a models folder.

## Windows application

Double-click `dist\Agent Orchestrator.exe` for the graphical launcher (`publish.ps1` builds it; it is stored with Git LFS, so `git pull` brings the latest). Download llama-server under **Options**, then start a chat in the **Code** view (see Code mode below): pick a folder, optionally add a `PROJECT.md` from the **Project** menu, and press **Start project**, which adds the workflow files automatically. **Project > Run one reviewed task, then stop** gives `--once` behavior.

The window follows the Image Parser design language: selectable themes (Dark Parchment is the default; Parchment is a light theme; Flat, Track Gold, Liquid Glass, OLED and Graphite are dark) with per-theme accent colours, a left navigation panel, and a two-column workspace with a draggable divider.

- The Code header's start button reads **Start project** until the folder has the workflow files, then *Start Task* for a project with no tasks yet, and otherwise **Resume Project — <task>**, naming the active task (from `TASK.md`) or the last one that passed (Ctrl+Enter).
- A project run's **model output** goes into the Code conversation, after the messages shown when it started: each agent's thinking, tool calls with results, and responses in execution order (a thin line marks where one model's output gives way to another's, in a project run and in a reply that hands a part to another worker), between a **PROJECT RUN** note and one saying how the run ended. Thinking and tool sections are collapsible (Ctrl+E / Ctrl+Shift+E expand or collapse them all). TASK TIME and TURN TIME sit in the Code header once a run has started.
- The **execution log** is saved per day in the data folder's `logs` (kept 14 days); **Project > Open run logs** opens the folder and **Copy run log** copies the last run's log.
- **Model details** (right column) has one card per role with the model name, weights, quantization, live tokens/sec, and total tokens for the current turn. Speed and token counts come from llama-server's `/slots` data.
- While a reply or a run is using the models, a stop icon appears to the left of **Send** (Ctrl+Shift+X). It stops the run, or the reply; stopping a run or closing the window also stops the llama-server and frees its models.

The launcher starts the engine with `--events`, which makes `orchestrator.py` print structured `@@AO {json}` lines alongside its normal log output. Plain command-line runs do not emit them.

**Context compaction.** Before each model call the engine estimates the prompt (characters ÷ 3.5). When the model's context size is known and the estimate passes 90% (`COMPACT_AT`) of what the reply's `max_tokens` leaves (at least half the window), or when the API rejects a request as too long for the context (once per call, then it retries), the history is compacted: the system message, the task and the most recent steps stay, and the steps in between are summarized by one quiet call to the same model (falling back to a list of the tool calls made) and appended to the task message under `CONTEXT SUMMARY`. The run, Chat and Code then carry on with the shorter history. The engine logs `[role] context compacted: <before> → <after> tokens` and emits `{"e":"compacted","role","before","after"}`, which the launcher shows as a muted line in the reply and a note in a project run's output. A history too short to drop anything from still fails with the context-length error.

Local models run on llama.cpp's llama-server. **Options > Model runtime > Download llama-server** fetches the latest llama.cpp Windows build from GitHub into `%APPDATA%\Agent Orchestrator\llama.cpp` (CUDA with its runtime when `nvidia-smi.exe` is found, else Vulkan, else CPU; **Update llama-server** replaces it). GGUF files are found in the Hugging Face cache and in the optional **Models folder**. The engine starts one llama-server on `127.0.0.1:8899` (several with `AGENT_ORCHESTRATOR_MULTI_MODEL`, see Local models below); the launcher stops it when the app closes and, with **Keep models loaded** off, after each chat turn.

Initialization adds these project-local files without overwriting existing files: `PROJECT.md`, `STATE.md`, `TASK.md`, `RESULT.md`, `REVIEW.md`, `ISSUES.md`, and `config.json`. Edit the initialized project’s `PROJECT.md`; the workflow maintains the handoff files.

Worker presets, **Add worker** and each role's **Settings** work without a project: with no project `config.json` they edit the launcher's own worker config (`%APPDATA%\Agent Orchestrator\worker-config.json`, first copied from this folder's template). With one they edit the project's `config.json` and mirror the change into the worker config, and new projects start from the worker config. The template `config.json` here is never written. **Copy full log** copies the complete output buffer, including lines outside the visible scroll area.

On the first run, the Planner reads `PROJECT.md`, a bounded project-file inventory, and recognized build manifests. It then fills only `validation_commands` in the project’s `config.json` and marks the project configured. If no commands can yet be justified, the workflow checks again after project files change. Model endpoints and loading settings are copied from the protected Agent Orchestrator template and are not generated by the model. To regenerate non-empty commands after changing build systems, set `project_configured` to `false` and run again.

The EXE is self-contained for .NET, but the workflow engine still requires Python 3.11 or newer on `PATH`.

## Setup

1. Put this workflow folder anywhere. Your code may be this folder or a different folder.
2. Replace the placeholder in the target project’s `PROJECT.md` with the full desired outcome and acceptance criteria.
3. In the PowerShell window that will run the controller, point the engine at `llama-server.exe` (the launcher downloads it into `%APPDATA%\Agent Orchestrator\llama.cpp`):

   ```powershell
   $env:AGENT_ORCHESTRATOR_LLAMA_SERVER = "$env:APPDATA\Agent Orchestrator\llama.cpp\llama-server.exe"
   ```

4. Make sure the three models' GGUF files are in the Hugging Face cache, or set `AGENT_ORCHESTRATOR_GGUF_DIRS` to the folder holding them (see Local models below).
5. Review the generated project-local `validation_commands` after the first run. Each command is an argument array, not a shell string.

Run the legacy pipeline against code in this folder:

```powershell
python .\orchestrator.py --pipeline
```

Run against another initialized project (the lead project run; add `--pipeline` for the legacy pipeline); its workflow records stay in that project:

```powershell
python .\orchestrator.py --project 'Y:\path\to\project'
```

Use `--once` to complete one reviewed task. Use `--non-interactive` for three independently served endpoints; set each role's `base_url` accordingly first.

## Automatic model switching

Each role's `auto_load` describes the model llama-server loads for it. The Planner, Implementer, and Reviewer are swapped one at a time on the same GPU; no three-model simultaneous load is attempted. Sampling is sent with each request and never reloads the model.

Set `roles.<role>.sampling.enable_thinking` to `true` or `false` to switch thinking on or off for that role's requests; leave it out to use the model's default. If a reply is cut off by the output limit while still thinking, it is retried once with thinking off before the run fails.

### Local models (llama.cpp)

Every role with an `auto_load` runs on llama.cpp's `llama-server.exe`; remote API roles are unchanged.

- `AGENT_ORCHESTRATOR_LLAMA_SERVER`: full path to `llama-server.exe` (download it in **Options**). Required for local roles.
- `AGENT_ORCHESTRATOR_GGUF_DIRS`: optional `;`-separated extra folders holding GGUF files.
- `AGENT_ORCHESTRATOR_MULTI_MODEL`: `never` (default; also any other value) keeps one server and stops the others before a different model loads; `always` starts each model on its own server beside the others on the next free port from the configured one, evicting nothing; `fit` does the same while the model's estimated VRAM (weights, scaled by `-ngl` when it is below the layer count, plus the KV cache for `-c`, or the model's context capped at 32768 when `-c` is absent, plus 10%) fits the GPU memory `nvidia-smi` reports free, else stops the least recently used servers until it does. A server this run already used is never stopped to make room. If `nvidia-smi` gives no figure, `fit` loads one model at a time, or beside the servers this run uses when it already uses one.

The model file is `auto_load.gguf_file` when set and present. Otherwise it is looked up, in order, in each extra folder (recursively, files whose path names the model, for example `Qwen3.5-4B` for `unsloth/Qwen3.5-4B-GGUF`) and in the Hugging Face cache (`HF_HUB_CACHE`, else `HF_HOME\hub`, else `~\.cache\huggingface\hub`, under `models--<org>--<name>\snapshots`). A file whose name contains `gguf_variant` is preferred, `mmproj` files are skipped, and a split model starts from its `-00001-of-0000N` part. If nothing is found, download the model from Hugging Face or add its folder in Options.

By default one server runs at a time on `127.0.0.1:8899` (top-level `"llama_port"` in `config.json` overrides; with several servers, the next free port above it), started with the role's `max_seq_length`, `gpu_layers` (`-1` = all), `cache_type_kv`, `n_batch`, `n_ubatch`, `reasoning_budget` (only `0` is passed) and `llama_extra_args`. A server already running with arguments that can serve the role is reused: the same arguments, except that a larger `-c` is fine and a thinking server serves a `reasoning_budget` 0 role with thinking off per request. A different model or other setting restarts it. The state is in `%TEMP%\agent-orchestrator-llama.json` as `{"servers": [{"pid", "port", "signature", "args", "model_file", "log", "last_used"}]}` (the older single-server object is still read) and each server's output in `%TEMP%\agent-orchestrator-llama-<port>.log`. The `loading` and `model` events carry the server's `port`; evicting a server under `fit` emits `unloading {role, model, port}`. A workflow run stops the servers it used when it ends; in chat and code mode they stay up until the launcher closes. `python orchestrator.py --unload-local` stops every recorded server and deletes the state file.

## Remote models per role

Any role can use a remote OpenAI-compatible API (OpenRouter, a cloud provider's OpenAI-compatible endpoint, another local server) while the others stay local. Give the role `base_url`, a `model` id and `api_key_env`, and no `auto_load`:

```json
"planner": {
  "base_url": "https://openrouter.ai/api/v1",
  "model": "openai/gpt-4o-mini",
  "api_key_env": "OPENROUTER_API_KEY",
  "timeout_seconds": 600,
  "sampling": { "temperature": 0.6, "max_tokens": 8192 }
}
```

`max_tool_call_chars` (optional, per role; set it under **Max tool call (characters)** in the model settings) caps one tool call's arguments in a Pi Code turn. A call that streams past it (a model looping inside one file write) is aborted, does not run, and the model is told to send the work in smaller pieces; 0 or empty is no limit. The call also shows live as a collapsible section (like thinking) with its code in a colour-coded block, and folds into the THINKING row when View thinking is off.

`model` is sent as the request's model id as is (no `/models` check), and the role is never loaded, unloaded or monitored. The key is read from the named environment variable and never written to config, logs or prompts. Paste it on the Remote API page instead of setting the variable: the app keeps it encrypted for your Windows account (`keys.json` in its data folder, DPAPI) and puts it in its own process environment under that name, so nothing is written to your user environment. Errors name the role and URL (for example `planner: API 401 from https://…/chat/completions (check the key in OPENROUTER_API_KEY)`). Keep `sampling` to parameters the API accepts: some reject llama.cpp extras such as `top_k` or `enable_thinking`. In the launcher, a role's **Settings** has a **Remote API** mode that writes these keys and keeps the local settings in `local_settings`; switching back to **Local** restores them.

**The Remote API page.** The **Remote API** item in the left navigation (below *New*) sets a worker up on a remote service without editing JSON. Pick a service (OpenRouter, OpenAI, Groq, Together, Fireworks, DeepInfra, Mistral, DeepSeek, xAI, Cerebras, Google Gemini, NVIDIA NIM, or a Custom URL), then a model from the list the service reports (or type its id), then **Apply to** one of your agents. The API key variable fills in for the service (for example `OPENROUTER_API_KEY`); paste the key into the page's API key box (encrypted for your Windows account, "Remove" forgets it), or set that variable in your environment and restart the app; a key saved in the app wins. The first time you open the page, a popup explains where to create a key for each service (**Key help** reopens it). For OpenRouter a provider table lists every provider for the model with input, output and cache-read price per million tokens, latency, throughput, uptime and image support (latency and speed show once an OpenRouter key is set); a shield after each name shows its data policy as OpenRouter's own page lists it (green: does not train and keeps no prompts; amber: may keep prompts but does not train; red: may train on them; none: unknown, or that page could not be read; hover for the wording); tick the providers you want, in order. The launcher saves them as `sampling.extra_body.provider` = `{"order": [...], "allow_fallbacks": false}`, so OpenRouter uses only those providers, in that order, and fails the request instead of falling back. Leave all unticked to let OpenRouter choose; other services ignore it. Below the table, three price controls (OpenRouter only): **Cheapest** adds `"sort": "price"` (the cheapest provider first), **Max in $/M** and **Max out $/M** add `"max_price": {"prompt": …, "completion": …}` in US dollars per million tokens (empty means no cap; OpenRouter refuses providers above it; the page also hides the models and provider rows listed above a cap, keeping models with no listed price, the chosen model tagged "over cap", and ticked providers marked "(over cap)" in the order), and **Use :floor** saves the model id with the `:floor` suffix (for example `z-ai/glm-5.3-flash:floor`) while the Model id box keeps the base id; an id that already has a variant such as `:free` cannot take it. Each part is written only when set, so the full shape is `{"order": [...], "allow_fallbacks": false, "sort": "price", "max_price": {"prompt": 0.5, "completion": 2}}`. Cheapest and `:floor` matter only when no provider is ticked; the max price always applies. The page shows the cheapest input and output price on offer; the cheapest provider is not always the best one (quantization, speed and reliability differ). A Custom URL sends no request, and no key, until you press Enter or **Load models**. In Agent details a remote agent shows `Remote: model @ providers` (then `· cheapest`, `· max $X/M in`, `· max $Y/M out` when set) with **Edit in Remote API** and **Switch to Local**; a local agent has **Use a Remote API…**.

## Chat mode

Role fallback: only the `planner` role (the base model) is required in `config.json`. An `implementer` or `reviewer` that is missing from `roles`, or set to `{"same_as": "planner"}`, uses the planner's settings (model, sampling, `auto_load`) everywhere, the project run included; the same model is not reloaded.

`python orchestrator.py --project <folder with config.json> --chat <request.json> --events --non-interactive` answers one chat turn instead of running the workflow. It needs only `config.json` in the project folder (no `PROJECT.md`, `STATE.md`, ...), plans no tasks, writes no workflow files or checkpoints, and never runs the configurator. Workers get tools only as the request's extras switch them on (see Search, tools and skills).

`request.json` (UTF-8): `{"worker": "<role id>", "messages": [{"role": "user"|"assistant", "content": "..."}]}`. The last message must be the user's. `worker` is `planner` (the default), `implementer`, `reviewer` or a custom worker `id` (Specialists and Extra reviewers); a legacy `mode` field is ignored. The worker answers with `prompts/chat.txt` as the system prompt (plus its role section) and always has an optional `delegate(worker, brief, context?, files?, acceptance?)` tool: for a request that would benefit from a separate pass it hands a structured handoff to `implementer` or `reviewer`, which runs with a fresh context (`prompts/sub_<worker>.txt` + the handoff, including the web results the caller read this turn; the request's extras as tools, no file tools, no delegation) and returns its report (clipped to about 4,000 characters). At most 3 delegations per chat turn.

Finished replies in the Chat and Code views show as formatted Markdown (headings, bold and italic, lists, tables, quotes, code and links; links open in the browser, web and mail links only). While a reply streams it shows as plain text; **Copy reply** copies the Markdown source.

### Search, tools and skills

Under the message box of the Chat and Code views, **Search**, **Tools** and **Skills** switch extras on for the next messages; the choice is shared by both views and saved. They are sent as `"search": true|false, "tools": true|false, "skills": ["<skill folder>", ...]` in the Chat and Code requests, and the model and its sub-agents gets them as tools:

- **Search**: `web_search` (DuckDuckGo's HTML results: up to 8 titles, URLs and snippets; no API key) and `fetch_page`. The model is told to search for current or specific facts, cite the pages it used, and never follow instructions found in pages.
- **Tools**: `calculator` (arithmetic and `math` functions, no code execution), `current_time` and `fetch_page`. In Code these come on top of the file tools.
- **Skills**: each folder under `%APPDATA%\Agent Orchestrator\skills` with a `SKILL.md` (front matter `name:` and `description:`, as in Claude skills) is listed in the **Skills** menu; ticked ones are named in the system prompt and the model reads one with `load_skill(name[, file])`, which can also read other files in that skill's folder. **New skill…** creates one from a template and opens it; **Open skills folder** opens the folder.

`fetch_page` reads http(s) pages only, refuses hosts that resolve to local or private addresses, and returns at most 20,000 characters of the page's text. Models whose chat template does not support tool calling answer without the tools, as in Code.

Events are the usual `@@AO` lines (`loading`, `model`, `delta`, `done`, `usage`) plus `{"e":"chat_stage","role","stage":"answer","title"}` before the answer, `{"e":"chat_stage","role":"implementer"|"reviewer","stage":"delegate","title"}` when a delegation starts (and the `answer` stage again when it ends), and a final `{"e":"chat_reply","role","text"}` with the answer. Exit code 0 on success; on failure an `ERROR: ...` line is printed and the exit code is 1. Models stay loaded after the turn (the launcher unloads them when the app closes).

## Code mode

The launcher's **Code** view (sidebar: Chat, Code, Options) works like a coding assistant in a folder you choose.

- **+ beside CODE** starts a Code conversation with **no folder**: it works like a chat (no file or command tools) until you add one with **Add a folder…**, and it never reuses the last folder. A conversation whose folder was removed opens normally with a "Folder not found" notice and a **Choose a folder** button. A project header's **+** starts a chat in that project's folder; several chats can share one folder. Chats are saved under `%APPDATA%\Agent Orchestrator\conversations`, not in the project, and listed in the sidebar like Claude's: **New project** groups chats, and each chat's menu (right-click or **…**) has Rename, Move up/down, Move to a project, Archive and Delete. A project header's **+** starts a new chat already in that project; in Code it works in the folder of the project's latest Code chat without asking (only a project with no Code chat asks for a folder). Drag a chat onto another chat, a project or **Recents** to move it, and drag a project onto another to reorder them. Archived chats sit in a collapsible **Archived** section. If the saved list can't be read, it is shown read-only so nothing is overwritten.
- Conversations in the **Chat** view are saved in the same list once they get a reply (marked with a speech bubble) and reopen in the Chat view with their worker.
- The Code header's **Project** menu holds the per-folder options: **Use a PROJECT.md…** (an existing one is backed up), **Edit PROJECT.md**, **Folders…** and **Stop after the first finished item**. The lead project run ignores task limits; they apply only to the legacy `--pipeline`.
- The workers start as one: **MAIN** (the Planner role, the base model) covers the Planner, Implementer and Reviewer roles, and its tab lists what it covers. **+** adds a separate Implementer or Reviewer (its own tab and model) or a custom worker; removing an added role runs it on MAIN's model again (`"same_as": "planner"` in `config.json`), and its activity shows on MAIN's card.
- Each Code message goes to the **lead agent** (MAIN); the **Lead:** chip names its model and opens its Options. It is the primary agent: like a frontier coding agent it plans with a short checklist (`todo`), does the work itself whatever its size, researches with the web tools when Search is on, verifies with `run_checks` and by reading files, and finishes with a short report of what changed and what is left. Delegating to the Implementer (edits files) or the Reviewer (reads files and runs the checks) is optional, for an independent check or a separate piece, with a structured handoff. It can list, read and search files, and create or edit files directly in the project folder.
- In Chat, the **To:** chip picks the worker to message (MAIN, an added role or a custom worker) and opens its Options; that worker can delegate parts to the others.
- **Project > Folders… > Add folder…** grants extra folders, each one **Read only** or **Full edit**. Nothing outside the granted folders can be read or written. `api_key.txt` and `.git` are always refused, and links or junctions that point outside are skipped.
- **Notifications** (Options): a desktop notification when a reply has fully finished (nothing queued left to send) or a project run ends, while the app is not the window in front; clicking it brings the app back. Off by default.
- **`/compact [focus]`** (Chat and Code): summarizes the conversation now, without a model turn (the built-in engine's summary, with the focus added to its prompt; in a Pi session, Pi's own `compact`). The reply gives the before/after tokens, and a rule under each context-compacted note marks where the summary begins.
- **Attachments**: the composer's **+** (the app's compact menu), **Ctrl+V** (copied files, or a copied picture saved as a PNG under `<data>\pasted`) or **drag and drop** onto the message box; up to 20 photos per message, also while a reply runs (they go with the queued message). Photos reach the model as images; on llama.cpp the vision projector (`*mmproj*.gguf` beside the model) is loaded unless **Disable vision** is on.
- **In-app browser for the model**: the lead's `browser` tool (`open` a file in the chat's folders, or a web address when Search or Tools is on; `read` the current page) opens and expands the app's browser on the page and returns its title, visible text and script errors. The prompts tell the lead to use it before any other browser. It runs as the app, outside the sandbox, with the browser's own sign-ins. The lead also drives the page with its own mouse and keyboard: `click` (by screenshot pixel or by visible text; left, right, middle, double, triple), `move` (hover), `drag`, `scroll`, `type` and `key` (any key of the keyboard: letters, digits, punctuation, F1-F24, the numpad, locks, modifiers and media keys, alone, as a chord such as `Ctrl+A`, or several in a row such as `Tab Tab Enter`). Input goes to the tab through the DevTools protocol, so the user's real mouse and keyboard are never used or blocked; a coloured ring in the page marks each action. Coordinates are pixels of the model's last screenshot, whose reply states the image and viewport size. The browser panel's **Let the model use mouse and keyboard** switch turns this off. Not reachable: a `<select>`'s native list (focus it and use the arrow keys), file pickers (a click on a file input or its label is refused), OS dialogs and the browser's own menus. The page's `alert`/`confirm` dialogs are cancelled and reported to the model (the user sees a normal message box for their own). Copy, cut and paste keys are refused, since the clipboard is the user's. An action that gets no answer from the page within 45 s ends with an error. Because the browser keeps the user's sign-ins, the model can submit forms on signed-in sites.
- **Computer use** (off by default; Options > General > Computer use): with the switch on and at least one application approved, the answering model (Chat, Code with or without a folder, the project lead, Pi; not its delegates) gets a `computer` tool. **Add application** lists the programs with a window open now, or browses for an `.exe`; only the listed programs can be used. Actions: `apps` (the approved applications and their windows), `open` (an app by name, started if it has no window, or a window by number; this is the one window the model may use for the rest of the reply), `screenshot`, then `click`, `move`, `drag`, `scroll` (wheel notches), `type` and `key`, the same as the browser's; `steps` adds up to 19 more actions to run right after, with one screenshot at the end (fewer model calls). Screenshots are at most 1280 px a side. While it drives, a large white arrow stands in for the mouse pointer (the system cursors are blanked and restored when it ends, when the app closes, or at the next start after a crash), the pointer glides with easing, and cyan rings ripple out where it clicks; none of these appear in its screenshots. Input is real (Windows `SendInput`): the pointer and keyboard focus move, so the user should leave the computer alone while it works. Every action first brings the window to the front, and refuses a point outside the last screenshot, on another application's window in front of it, or after the window moved or resized. Keys go only while that application has the keyboard. The Windows key, Alt+Tab, Ctrl+Esc and copy/cut/paste are refused. A banner at the top of the screen says the model is driving. **Esc** pressed on the real keyboard stops it: the tool refuses every further action and the reply is stopped. Not usable: admin (elevated) windows, which Windows protects from other programs, and pop-up menus that open outside the window's area (they are not in the screenshot).
- **Skill completion** (Chat and Code): a message that starts with `/` or `$` lists the matching installed skills, and after `/` the app's commands (`/compact`), above the box with what each does; Up/Down move the highlight, Tab or Enter completes, a click completes, Esc closes. A message that names a skill as `/name` or `$name` sends that skill with the turn, switched on in the Skills menu or not.
- No `PROJECT.md` is needed to start. Discuss the project over as many messages as you like, then say `init-projMD` (or `/init-projMD`, or ask for a PROJECT.md): the lead loads the bundled `init-projMD` skill (always offered in Code) and writes `PROJECT.md` itself from the conversation, its research and the folder, then stops. You can also bring your own `PROJECT.md`.
- `PROJECT.md` is the plan, not a mode: say "use PROJECT.md and begin work" (or "continue") and the same lead reads it, checks the files and implements the next work directly in the conversation.
- **Start project** is the separate autonomous run: the workflow files are added (an existing `PROJECT.md` is kept), and the lead project run starts with this conversation's tools, folders, sandbox and effort; its output streams into the conversation. The button starts it, or say `start-project` (or `/start-project`, `$start-project`): the lead loads the bundled `start-project` skill, checks `PROJECT.md` and calls `start_project`, and the run starts when that reply ends. `start_project` is offered only on a turn whose latest user message invokes the skill, so a model never starts a run on its own.
- **Context**: under the Code header, right-aligned with Start project, one card per worker stacks vertically, the lead's ("Main Context") first; click a card to open its breakdown. It slides left while a collapsed-rail worker card is open. The worker column's Context section also has one card per worker that worked in the conversation ("Main Context", "Implementer Context", ...), from Code turns and project runs alike, saved with the chat. A model loading or the models being unloaded drops every worker's card to 0 (nothing is left in its window); the lead's keeps its last value, because its next call sends the whole conversation again. A compaction updates the compacted worker's card.

Command line: `python orchestrator.py --project <folder with config.json> --events --code <request.json>`.

- `request.json` is `{"action": "chat"|"write_project", "worker": "<role or custom id>", "messages": [...], "folders": [{"path": "<absolute>", "access": "write"|"read"}]}`. Action `chat` always runs the lead (`worker` and a legacy `mode` are ignored); `write_project` uses `worker` (default `planner`).
- `folders[0]` is the project and is always writable.
- The lead's tools are `list_files`, `read_file`, `search_files`, `write_file`, `replace_text`, `todo`, `run_checks` (syntax, JavaScript code check, page load and `validation_commands` on the project root), `delegate(worker, brief, context?, files?, acceptance?)`, `load_skill` (the bundled `init-projMD` plus the enabled skills) and the enabled Search/Tools extras. A sub-agent starts fresh (`prompts/sub_<worker>.txt`, the handoff with the lead's web results of the turn, the folders) and inherits the extras; the Implementer gets the first five tools, the Reviewer the first three plus `run_checks`; neither can delegate. `max_tool_steps` limits each loop and `max_delegations` (default 6) the delegations per turn.
- Events: every tool call is a `tool` event (sub-agents' carry their own role), `chat_stage {role:"planner",stage:"lead",title}` when the lead starts and after each delegation, `chat_stage {role:"implementer"|"reviewer",stage:"delegate",title}` when one starts, then `code_project {role,path}` (action `write_project`) and the final `code_reply {role:"planner",text}`.
- Chat and Code turns share the GPU, so only one runs at a time and none during a project run.

### Command sandbox (run_command)

- **Permissions** (the Code composer's dropup left of Search; sent as the request's `permissions`): **Allow Safe** (default) runs commands in the sandbox without asking and asks before network access or writing other folders; **Always Ask** also asks before every command; **Allow All** grants network and extra-folder requests without asking. Every mode keeps the sandbox; folders `grantable` refuses stay refused, and a risky git repository is always asked about.
- **Allow similar commands for this session** (in a request popup): the launcher answers later requests of the same kind for the same program (`command_key`: `npm test` and `npm install` are both `npm`), or the same folders for write requests, in that chat without asking, until the app closes.

Both Code engines, and their Implementer and Reviewer, have `run_command(command, shell?, timeout_seconds?, request_network?, request_write?, reason?)`: cmd or PowerShell commands (build, tests, scripts, git) started by the engine — never by the model's process — inside a Windows **AppContainer** (`sandbox.py`). Windows enforces it, and every child process inherits it. `run_checks` runs the project's `validation_commands` the same way, so no model-written code runs with your own rights in a Code turn:
- **Files.** One container per conversation (the request's `session`); the Reviewer gets its own read-only container and cannot ask for more. The engine grants the container exactly the turn's folders (write, or read for read-only folders) plus a private temp folder, as inheritable ACEs for its SID. Grants that are no longer wanted are removed, and the record (`<data>\sandbox\grants`) is written before every change, so a crash never leaves an unrecorded grant. The rest of the disk is unreadable, or read-only for Windows' own folders. A folder that is, holds or lies in the Agent Orchestrator folder is never granted.
- **Skills, read-only.** Every container (any permission mode) also gets read and execute, never write, on your skills folder (`<data>\skills`, found beside the sandbox's `home`) when it exists and is a real folder, not a junction or link, so a skill's scripts and templates run in place. The Code system note names it. Nothing else in AppData is granted, and `request_write` keeps refusing the skills folder.
- **`.git` stays read-only.** Its hooks and config run later as you. Windows ignores deny entries for an AppContainer's own SID, so every `.git` in a write folder stops inheriting instead, with its ACL saved and restored exactly when the grant goes. That covers nested repositories and the `.git` files of worktrees and submodules (dependency and build folders are skipped). A repository a command creates is checked after the command: if it has hooks, config that names programs, or is a `.git` file, you are asked to keep it or quarantine it (its `.git` is renamed). From then on it is read-only too.
- **Network.** Off: the container has no network capability, so loopback (the model servers) is closed too. Settings > **Command sandbox** can allow outbound internet (`internetClient`: no LAN, never loopback) for every command; otherwise `request_network`, or output that looks like a blocked network call, asks you in a dialog.
- **Extra write folders.** `request_write` asks before granting a folder for one command. It takes plain `C:\...` paths only, compared by their real path (no junction, link, UNC or `\\?\` spelling). It refuses drive roots, your profile or anything above it, AppData, Desktop and the dot-folders of your profile (`.vscode`, `.config`, ...), and anything that is, holds or lies in: the Agent Orchestrator folder, the launcher's data folder, Python's installs and site-packages, Windows, the program folders, ProgramData, the Startup and PowerShell profile folders, or a folder on PATH. An approval holds for that one command, and the command still runs in the container. Commands run one at a time.
- **Secrets.** Variables whose names contain KEY, TOKEN, SECRET, PASSWORD or AUTH are not passed to the command. Their values, the secret-named values of `HKCU\Environment` and `api_key.txt` are replaced by `[secret removed]` in the output before the model sees it. Windows lets every AppContainer read parts of HKCU, so while a user environment variable has a secret-looking name, **commands are refused until the setup has closed `HKCU\Environment`**, where user environment variables live. PowerShell 5.1 reads that key as it starts, so while it is closed commands use cmd. To get PowerShell back, move the secret out of your user environment variables, then run `sandbox.py --unprotect-environment --state <data>\sandbox`. With no secret-looking variable, the setup leaves the key readable. In PowerShell any error record (a refused write, say) makes the command exit 1. The rest of `HKCU\Software` stays readable as Windows ships it, so keep secrets out of the registry. Redaction is a plain text replacement: an encoded or split secret gets through. Fully closing the registry would need commands to run under a separate Windows account.
- **Limits.** A command runs at most `timeout_seconds` (default 120, at most 1800) in a kill-on-close Job, so a timeout ends its whole process tree. Output is clipped to 30,000 characters.
- **Setup.** **Set up sandbox access…** does two things:
  1. As you, without elevation (`sandbox.py --protect-environment`): it removes the AppContainer entries from `HKCU\Environment`'s ACL, saved so it can be restored, which lets commands run.
  2. As administrator, once (`sandbox.py --setup`, a UAC prompt): every container carries this app's capability (`agentOrchestratorCommandSandbox`), and that capability may then list the fixed drives' roots and `C:\Users` (names only, written without walking the drive) and read the folders of the developer tools on PATH (Python, Node.js, Git, .NET, Java, ...). Only this app's containers gain that access. PowerShell needs the drive roots, so until this part has run, commands use cmd. FAT32 and exFAT drives keep no permissions, so they are skipped; the sandbox cannot open them anyway.

  `sandbox.py --unprotect-environment` and `--undo-setup` (with `--state <data>\sandbox`) reverse them. The engine also lets the capability list the folders above each granted folder that you own.
- The approval protocol: the engine emits `{"e":"approval","id","kind":"network"|"write","detail","reason"}` and waits for one stdin line `{"id","allow"}`. Without a launcher the answer is no.

### Pi Code engine (optional)

Settings > **Code engine** chooses who runs a Code turn's agent loop: **Built-in** (above) or **Pi** ([pi.dev](https://pi.dev), `@earendil-works/pi-coding-agent`). **Install Pi** runs `npm install --ignore-scripts` of the tested version (1.4.0) into `<data>\pi`; Node.js 22.19+ must be on PATH. The launcher passes the installed `cli.js` as `AGENT_ORCHESTRATOR_PI`; without it the engine falls back to a 1.x `pi` on PATH and refuses older ones.

With `"engine": "pi"` in the Code request the engine loads the lead's model as usual, then runs `pi --mode rpc` in the project root on that model (provider `ao`: the role's endpoint, sampling, thinking switch and `max_tokens`, written to a per-turn `models.json`), with only Pi's `read`, `edit` and `write` tools and none of its project-local configuration, extensions, MCP or shell. `pi/agent_orchestrator.ts` sends every `read`/`edit`/`write` path through a localhost gateway in the engine, which applies the same folder grants and protected files as the built-in tools (a refused path blocks the call; an accepted one is replaced by the absolute path that was checked; spellings Pi would rewrite — a leading `@` or `~`, `file:` URLs, `/c/` paths, Unicode spaces — are refused, and `read`/`edit` need an existing file), and registers the engine's own `list_files`, `search_files`, `todo`, `run_checks`, `delegate` and Search/Tools extras, which run in `orchestrator.py`. Skills, the bundled `init-projMD` included, load as Pi skills. The system prompt adds `prompts/lead_pi.txt` and the FOLDERS block to Pi's own. Each Code conversation keeps one Pi session (`<data>\pi\home\sessions`, the request's `session` id), so later turns see earlier tool calls and results; a session's first turn gets the earlier messages as text once. Pi compacts the session itself (reserve `min(n_ctx/2, max_tokens+4096)`, keep `n_ctx/4`). Pi's events become the usual `delta`, `done`, `usage`, `context`, `tool` and `compacted` events; delegation works as in the built-in engine, and the lead's model is ensured again after a worker. Chat, Start project and the pipeline do not use Pi.

## Custom workers

`config.json` may hold an optional top-level `custom_workers` array. Absent or empty, the run behaves exactly as before.

```json
"custom_workers": [{
  "id": "8f0c...", "title": "Tester", "kind": "specialist",
  "description": "Writes and runs unit tests for a feature.",
  "system_prompt": "You are a meticulous test engineer...",
  "expected_model_contains": "...", "display_name": "...", "timeout_seconds": 600,
  "auto_load": {}, "sampling": {}
}]
```

`id` is stable and unique and is the `role` of every event the worker emits. `title` is unique (case-insensitive) and never `Planner`, `Implementer` or `Reviewer`. The model fields (`base_url`, `expected_model_contains` or `auto_load.model_path`, `auto_load`, `sampling`, ...) have the same meaning as in `roles.<role>`, and the worker is loaded, reloaded and unloaded the same way. An entry with an unknown `kind`, a reserved or duplicate `id`/`title`, a missing `base_url`, model or `system_prompt`, or (for a specialist) a missing `description` is ignored with a `[workers]` warning.

- **Specialist** (`"kind": "specialist"`): listed in the Planner's TEAM section with its description. The Planner may add `"worker": "<title>"` to a task (case-insensitive; an unknown name triggers the usual correction turn, and the choice is stored in the task, so it survives a resume). The Specialist then does that task instead of the Implementer, with the same tools, file scope, syntax check and unverified-report handling. Its system prompt is the standard implementer prompt followed by a `YOUR ROLE: <title>` section holding `system_prompt`.
- **Extra reviewer** (`"kind": "reviewer"`): after the Reviewer passes a task and the syntax check passed, each Extra reviewer (config order, read-only) reviews it with the standard reviewer prompt followed by its own `YOUR ROLE` section. The task passes only when the Reviewer and every Extra reviewer pass. If any fail, the round fails: their defects, prefixed with the reviewer's title, go to the next round as feedback and into `REVIEW.md`. All Extra reviewers run each round so one round carries all their feedback; none run when the Reviewer fails. A run stopped while they check resumes there (checkpoint phase `extra_reviewing`) without re-running the Implementer or the Reviewer.

## Behaviour check

For web projects (an `index.html` in the project root, or `"behaviour_check": {"page": "<relative path>"}` in `config.json`) the page is loaded headlessly before planning and after each implementer round, right after the syntax check: the project is served on `127.0.0.1` and opened in a fresh browser profile (empty localStorage), and uncaught errors, unhandled promise rejections, `console.error` calls and missing scripts/stylesheets are recorded. Any error fails the round without calling the Reviewer and goes back to the implementer as feedback; a clean load gives the Reviewer a `BEHAVIOUR CHECK` block with a visible-text sample, and errors found before planning make the Planner schedule a fix first. It needs Edge or Chrome (standard install paths or on `PATH`); set `behaviour_check.browser` to a Chromium executable to choose one. Without a browser the check is skipped with a `[behaviour]` note. `"behaviour_check": false` turns it off.

For web tasks the Planner adds `"acceptance"` steps (at most 12) that the check runs in order on the fresh page after it loads, so a task passes only when its feature works in the browser, not merely when the page loads. Actions: `{"do": "click"|"fill"|"select"|"check", "selector": "#id", "value": …}` (`fill`/`select` fire `input` and `change`; `select` matches an option's value or text; `check` takes `true`/`false`), `{"do": "goto", "hash": "#view"}`, `{"do": "wait", "ms": 300}` (max 2000). Checks: `{"expect": "text", "selector": "#list", "contains": "Gaming PC"}` (visible text), `{"expect": "visible"|"hidden", "selector": "#id"}` (the element must exist), `{"expect": "count", "selector": "#list li", "min": 1, "max": 5}`, `{"expect": "storage", "key": "builds", "contains": "Gaming PC", "json_length_min": 1}` (localStorage), `{"expect": "no_errors"}`. Selectors are CSS strings of at most 200 characters; malformed steps are a contract error that goes back to the Planner. The steps are listed in `TASK.md`, so the Implementer builds to their selectors. The first failing step, or a page error raised during a step, fails the round with its detail (for example `acceptance step 3 failed: {…} — expected text 'Gaming PC' in #build-list; got ''`) and the steps after it are not run. When every step passes, the Reviewer sees each one ticked in the `BEHAVIOUR CHECK` block; a web task without steps gets the load check only, and the block says so.

## Code check

For projects with `.js`/`.mjs` files a static check runs after the syntax check and before the behaviour check (and in the implementer's own self-check). It reads the project's scripts and pages (skipping `node_modules`, dot folders and files over 1 MB) and flags calls such as `DataStore.addBuild(...)` or guarded references (`DataStore.fn ? ...`, `X && X.fn`, `typeof X.fn`) to members a project namespace object does not define, naming close matches, and `getElementById`/`querySelector('#id')` lookups of ids no page or script creates. Namespaces it cannot resolve confidently (spread, computed keys, `Object.assign`, other dynamic code) are skipped. On lines the task added it also flags stubs (`would go here`, `TODO`/`FIXME`/`placeholder` comments, `not implemented`, always-true assertions) and existence checks around the project's own functions. New issues fail the round like syntax errors; contract issues that were already there are listed to the Reviewer as pre-existing, and before planning they are given to the Planner so a task fixes them. `"code_check": false` turns it off.

## Project contract

Before the first task the Planner writes the project contract (`prompts/contract.txt`) from PROJECT.md and the current files, and the orchestrator saves it as `CONTRACT.md`: a short header plus one ```json block with `files` (path, purpose and, for pages, the scripts/stylesheets it `loads`), `ids`, `functions`, `storage_keys` and `notes`. Models cannot edit it; a task's optional `"contract_changes"` (same form, merged by path/id/name/key) updates it before the task runs. The Planner, Implementer and Reviewer all see it as `PROJECT CONTRACT`. It is enforced: acceptance steps selecting `#id` must use contract ids (the plan is corrected otherwise), and the code check fails a round when a contract page stops referencing an existing file it `loads` or a script looks up an element id the contract does not list (pre-existing issues are only reported). A missing or unreadable `CONTRACT.md` is regenerated, so Restart Project rebuilds it. `"contract": false` turns the whole feature off.

Whenever the contract is written or amended, the orchestrator scaffolds the web files it names that do not exist yet, so the page wiring is never left to a model: each missing `.html`/`.htm` page gets a minimal HTML5 page with a `<link rel="stylesheet">` for every `.css` it `loads`, a `<script src>` for every `.js`/`.mjs` (`type="module"` for `.mjs`) at the end of `<body>`, and an empty element for each contract id on that page (ids without a `file` go to the only page, if there is one) inside `<main>`; each missing `.js`/`.mjs`/`.css` file is created holding a one-line comment naming its purpose. Existing files are never changed, and other file types (`.py`, `.cpp`, `.h`, ...) are left to the tasks. It prints `[scaffold] created ...`. `"scaffold": false` turns off only the scaffolding.

## Safety and recovery

- Paths are resolved beneath `--project`; absolute paths and `..` escapes are rejected.
- Workflow records cannot be edited by the models.
- Only planner-approved files are exposed per task.
- A task can ask for more files once: the Implementer ends its report with `NEEDS_FILES: a.html, b.js — reason`, or Reviewer/check defects name the same file outside the allowed files in two consecutive rounds. The Planner approves or rejects; an approval adds at most the requested files (never workflow records, at most two over the task limit) from the next round on, without extra rounds, and survives a resume. A rejection's reason goes into the feedback and the ISSUES.md entry.
- Failed review gets at most two repair attempts by default.
- Malformed JSON, invalid Planner task contracts, and invalid Reviewer verdicts get at most two format/scope correction attempts.
- Model JSON is read tolerantly but never guessed: think blocks and surrounding prose are ignored, and only lossless slips (comments, trailing commas, smart quotes, raw newlines in strings) are fixed. A reply cut off or without JSON is re-asked from its original prompt with thinking off instead of being "repaired"; repairs also run with thinking off and keep the role's output format, followed by one fresh attempt. A Reviewer verdict that still cannot be read counts as a FAIL round (never PASS) and the loop continues; a Planner reply that cannot be read stops the run, which can simply be restarted.
- `STATE.md` changes only after reviewer PASS.
- `TASK.md`, `RESULT.md`, and `REVIEW.md` preserve the latest handoff.
- An implementer that prints tool calls as JSON text instead of calling the tools has them executed anyway; one that never writes a file is stopped rather than passed to the reviewer.
- Unreviewed changes left by an interrupted attempt (resume) or an earlier round are flagged to the implementer as PRIOR WORK; if it reports them complete without writing, the reviewer still checks the full diff against the task start instead of the task being blocked.
- A reply cut off at the output limit is logged; a truncated tool call is never executed and the model is sent back to write in smaller pieces, then the run stops asking to raise `sampling.max_tokens`. A prompt over the context window stops with a request to raise `auto_load.max_seq_length`.
- The llama-server is stopped when a run ends, whether it passed, failed, or was stopped.
- Stop with Ctrl+C. Re-run after inspecting the latest workflow records.

This is not a security sandbox. A local model allowed to edit project files can still write harmful source code. Use version control or a disposable copy of valuable projects.
